# Audio and diagnostics manual acceptance

These procedures are **not recorded as passed** by automated tests. Use the Windows desktop candidate, normal user rights and the exact endpoint you intend. Browser preview cannot collect Windows evidence.

1. Open Diagnostics, choose the desired inventory scope, and Run diagnostics. Confirm no sound, recording indicator or setting change starts. Pause/resume/cancel a scan; inspect collection errors and explicit Not tested/Not supported coverage. Reconnect only your intended device safely and refresh. Do not interpret supporting node counts as a physical device count.
2. Open a mouse/keyboard candidate. Inspect logical collections and Windows HID capabilities under Stats for nerds. Select each source separately and perform controlled input in the focused test area. For the four keyboard sources, record exactly which responds to your keyboard; do not assume all four are that keyboard. Test X down/up/repeats and mouse movement/buttons/wheel. Record dongle/receiver ambiguity and empty/nonresponsive sources.
3. Open Audio tests. Confirm Windows names, flow, active/inactive state and default roles. A remembered unplugged/disabled entry must not start a stream. Select the exact CMF/headphone/speaker endpoint if it appears; Windows metadata alone may not identify its transport/model.
4. Lower normal listening volume yourself. Approve the bounded quiet tone, then start L/R or tone. Confirm which channel you actually hear, and record yes/no/unknown separately from API completion. Stop early, switch apps and navigate away in separate tests; confirm streams cease. Disconnect during a test; expect an interrupted/failed/inconclusive result, never fabricated success. No automatic volume or routing changes should occur.
5. For the noisy microphone, choose the exact recording endpoint. Approve an eight-second local measurement. Measure a quiet interval, then normal speech from a controlled distance on the same endpoint/format. Record per-channel RMS/dBFS, peak, near-full-scale/zero fraction, frames, format and stream flags. Describe whether static was heard through your separate listening/comparison method; AnyDevice does not replay speech. These observations do not establish a defective microphone. Change one external factor at a time (distance/environment/port/known-good device) and repeat to distinguish hypotheses.
6. Stop/blur/navigate/close during separate microphone intervals. Confirm the Windows privacy indicator clears. Verify another application can use the endpoint afterwards. Never call fixture tests proof of cleanup on a physical driver.
7. If the intended endpoint is muted, review the proposal without applying it. Verify name, exact effect, risks and rollback. Apply only after explicit checkbox approval. Check native readback, then repeat the functional test. Separately approve restoring mute and check readback. Change mute externally between proposal/apply to test stale-state rejection. Do not apply to an intentionally muted endpoint merely to complete testing.
8. Prepare a sanitized report. Confirm session feedback association and numerical evidence, no names/IDs/free text, no typed text and no PCM/audio samples. Save locally. The strict frontend schema must reject extra audio payload fields before native saving; the Rust saver validates the envelope and total size. Closing the app clears volatile sessions; export evidence first.

Record app hash/source commit, Windows version, endpoint alias, procedure, actual measurements, cleanup and uncertainty. Audio listening/capture, device disconnect and repair tests still require user-operated acceptance before release. Automated fixtures validate code paths, not the connected physical hardware.
